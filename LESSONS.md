- 2026-08-25: The Alpaca MCP connector has intermittently failed to attach to the session on 4 of ~9 hourly runs today (11:56, 12:56, 16:07, 16:56 UTC), despite ListConnectors always reporting installState=connected/enabledInChat=true at the org level — the actual tool set is simply absent from the session (confirmed via ListMcpResourcesTool/ToolSearch). It has self-resolved on the next run each time so far without human intervention, but this means position monitoring (stops, trend exits) has real, recurring multi-hour gaps. Human should investigate the root cause of the connector attach flakiness; this is a platform/session reliability issue, not a strategy issue, and no guardrail changes are implied.
- 2026-08-26: A BTC/USD position (opened 2026-08-24) spiked to peak_R ≈ 1.99-2.08 intraday on 2026-08-25 around 02:00 UTC (bar high 81218.27) but was never scaled out at +1R, because the profit-taking check only runs at each hourly snapshot and price had already retraced back below +1R by the next run. Ten consecutive journal entries (2026-08-26T11:00 through 15:05) flagged the narrowing EMA20/50 gap and thin stop margin as a risk before the position was finally stopped out at 15:02 UTC for a realized loss of about -1.05R — giving back the entire peak gain plus more. This is a structural gap in hourly-cadence scale-out logic, not a signal-quality problem: intra-hour bar highs are already fetched every run and could in principle trigger a retroactive scale-out/stop-tightening even when the *current* price has since pulled back. Human should review whether the profit-taking rule should key off the highest high since entry (already computed for peak_R) rather than only the live price at each run boundary; no guardrail has been changed unilaterally.
- 2026-08-27: The 07:51 UTC run's `strategy.py --state state.json --out decisions.json` call exited non-zero with `<urlopen error Tunnel connection failed: 403 Forbidden>` while fetching 1H bars directly from `data.alpaca.markets`. The session's agent-proxy status confirmed the gateway rejected the CONNECT to `data.alpaca.markets:443` as a straight 403 policy denial, distinct from the earlier MCP-connector attach flakiness (get_account_info/get_all_positions/get_orders all worked fine via the Alpaca MCP tools in the same run). If this host is durably blocked by org egress policy in this environment (rather than a one-off gateway hiccup), every future run will fail identically and no fresh signal will ever be produced until either the egress allowlist includes `data.alpaca.markets`, or `strategy.py`'s bar fetch is rerouted through an MCP data tool instead of a direct `urllib` call. Human should check whether this recurs on the next run and, if so, treat it as a platform/network-policy fix, not a strategy change.
- 2026-08-27 (08:20 UTC): A fully-flat-account ETH/USD continuation entry sized by strategy.py at 1.00% equity risk (qty=38.9459, notional=$97980.48 against $98350.74 cash) was REJECTED by Alpaca with `insufficient balance for USD (requested: 99994.8, available: 98350.74)` -- the broker required ~2.05% more USD than the computed notional, i.e. a real notional/slippage buffer Alpaca applies to market crypto buys that strategy.py's cash-cap sizing does not account for. This was a near-max-cash entry (spending ~99.6% of available cash), which is exactly the case where a ~2% buffer tips it into rejection. No order/stop was placed; the run correctly declined to resize or re-chase and left the account flat. Human should consider whether strategy.py's cash-cap should reserve a small buffer (~2-3%) below available cash for market crypto buys specifically, so a good signal near the cash ceiling doesn't silently fail at execution time. No guardrail has been changed unilaterally.
